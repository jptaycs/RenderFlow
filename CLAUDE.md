# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

RenderFlow is an AI video production **orchestration platform**: topic or script in → narrated, rendered MP4 out. It coordinates external AI providers (LLM, image, TTS, avatar) behind swappable interfaces — it is not a model itself. Target: long-form YouTube documentaries (20–30 min), currently at the Week-1 walking-skeleton stage producing short videos end-to-end.

`AGENTS.md` points here; this file is the single source of truth — keep it honest as things change.

**Documentation rule: every change updates this file, in the same session.** If a session changes behavior, adds/renames a file or env var, installs a dependency, switches a provider or voice, learns a provider quirk the hard way, or verifies something against a live service — record it here (Current state, Commands, Configuration, Provider notes, Layout, whichever fits) before finishing. Anything not written down here is knowledge the next session doesn't have.

## Current state

Working today, verified against live services:

- Synchronous CLI pipeline: scene plan → images → voice → FFmpeg 1080p MP4
- Providers: Claude (LLM, untested live — no API key yet), Pollinations + Flux-Replicate + Pexels (image — Pexels is stock-photo *search*, not generation; opt-in, see Provider notes), Kokoro (**default TTS** — local, natural prosody) + Piper + ElevenLabs (TTS)
- Resumable asset generation (completed assets skip on re-run), per-asset cost tracking
- Talking-avatar scene contract with four providers: `wav2lip-local` (**default in practice** — free unlimited local lip sync + camera push-in, verified live, ~real-time on CPU), `ffmpeg-still` placeholder (static image + voice; no lip sync), `sadtalker-replicate` (paid lip sync + real head motion via Replicate; written, unverified — needs a funded `REPLICATE_API_TOKEN`), and `memo-hf` (free HF Space, demo-only: 4s audio cap)
- Piper narration pacing: `RENDERFLOW_TTS_LENGTH_SCALE` + sentence-pause insertion (see Provider notes)
- Fast visual pacing: scripts split into ~5-second scenes (clause-level splits for long sentences); image prompts are written as realistic photo captions with anti-AI-look negative prompts. Composition rule: **no visible human face at all** (strengthened 2026-07 from "no lone close-up," which still allowed faces in wider shots, per direct client feedback) — if a person appears, show them from behind/silhouette/distance/hands-only, enforced in both LLM prompts and the local prompt builder + negative prompts. `_local_image_prompt` leads with the constraint *before* the narration content (diffusion models weight earlier tokens more heavily), but prompt wording alone is **still not reliable** on abstract narration with no concrete noun ("the difference is not fancy technology") — Pollinations/Flux folds `negative_prompt` into plain text rather than true CFG-negative conditioning, so it's a suggestion the model can ignore.
- **Face-detection retry** (`pipeline/facecheck.py`): because prompt wording alone isn't reliable enough, scene-image and thumbnail-background generation (`assets._generate_face_free`, NOT the avatar portrait or thumbnail reaction face — those are supposed to have a face) now check their own output with OpenCV's YuNet DNN face detector and regenerate (fresh random seed each call) up to `MAX_FACE_RETRIES = 3` times if a face covers ≥12% of the frame's shorter side; if still failing after 3 tries, keeps the last result and logs a warning rather than blocking the scene. Verified live: converts some previously-100%-failing abstract lines to face-free within 1-2 retries, but a genuinely stubborn line can still fail all 3 attempts — an honest mitigation, not a guarantee. **Do not use `cv2.CascadeClassifier`/Haar cascades** — this opencv-python build (verified 5.0.0) removed that API entirely (`AttributeError`, not just missing data files). The YuNet ONNX model (~230 KB) auto-downloads once to `.cv2_models/` (gitignored) — small enough to skip a dedicated setup script, unlike wav2lip/kokoro.
- **SaaS layer (Phase 1, added 2026-07): multi-user auth + Postgres + Celery/Redis job queue.** The project is pivoting to a subscription SaaS (target: YouTube AI-content creators); this phase built what billing will need — accounts, project ownership, a real worker queue — billing itself (Stripe/Paddle) is a later phase. Datastores run via `docker-compose.yml` (postgres:16 + redis:7; needs Docker Desktop or `colima start`); the API and Celery worker run on the **host** from `.venv` because the pipeline needs host ffmpeg and the local model dirs. Pieces:
  - `renderflow/db.py` — SQLAlchemy models: `User` (email, bcrypt hash, `tier`, `is_admin`), `Project` (owner, slug unique **per owner**, `dir_path`), `Job` (kind, argv, `queued→running→succeeded|failed|cancelled`). Portable column types (JSON not JSONB) so tests run on in-memory SQLite. Schema via `create_all` on startup; Alembic deferred until the first post-launch schema change.
  - `renderflow/auth.py` — email+password (bcrypt, 8–72 chars enforced — bcrypt truncates at 72 bytes), itsdangerous-signed session cookie (httponly, samesite=lax, 30 days, `secure=False` until deployed behind TLS). **The first user to register becomes admin and adopts every legacy `projects/<slug>` dir** (`db.adopt_legacy_projects` — rows point at the old flat location via `dir_path`; files are never moved, so absolute asset paths inside scenes.json stay valid). Login returns the same 401 for unknown email and wrong password (no account probing).
  - `renderflow/tasks.py` — Celery worker (broker+backend = Redis). One task, `run_pipeline(job_id)`: spawns `make_video.py` exactly like the old api `_spawn` (own process group so cancel kills wav2lip/ffmpeg children too), records pid on the Job row, marks succeeded/failed (+run.log tail in `error`). **Cancellation (single-host design)**: the API marks the row `cancelled` *then* kills the pgid — commit order matters, the worker's post-`wait()` check must see "cancelled" or it would overwrite it with "failed"; queued jobs are `revoke()`d + status-checked at task start. When workers move off-host this must become a worker-side signal (no shared pid namespace). On worker boot, `recover_orphaned_jobs` fails any `running` row (killing its subprocess if somehow still alive — two writers on one scenes.json is the danger); replaces the old `run.pid`-file recovery, which is gone.
  - New projects live at `projects/u{user_id}/{slug}` (per-user slug namespace). The worker passes `--projects-dir` to make_video.py as a **CLI flag, never env** — `load_dotenv(override=True)` clobbers inherited env vars (the documented dotenv gotcha).
  - **Subscription paywall with trial credits (Phase 2, added 2026-07, `renderflow/billing.py`)**: every new account gets `TRIAL_CREDITS = 3` videos (`User.trial_credits`, decremented permanently on create — deleting a project does **not** refund, blocking create/delete/create abuse); after that an **active subscription** is required (`User.tier` = a `PLANS` key + `User.subscription_expires_at` in the future), granting a per-calendar-month allowance derived by *counting* the owner's projects (never a stored counter). `PLANS` (config.py): starter $19/10 videos, creator $49/30 — one source of truth for enforcement *and* the pricing UI. Only project **creation** is gated (402 + the frontend opens the pricing modal); resume/regenerate/layout/thumbnail on existing projects stay free — the credit bought that video. Admins are always unlimited. `billing.entitlement()` is the single source of truth, returned in every `/api/state` poll (drives the sidebar "Trial · N videos left" / "Starter · N of M left this month" line). **Payments are NOT integrated yet** — `POST /api/billing/checkout` is the Stripe/Paddle seam: with `RENDERFLOW_DEV_CHECKOUT=1` (local only) it activates the plan instantly for 30 days; otherwise it returns 503 "payments not configured". `POST /api/billing/grant` (admin-only) manually grants a plan for N months — the operator's lever until real payments exist. The two new `users` columns are migrated in-place by idempotent Postgres-only ALTERs in `db.init_db()` (create_all never alters existing tables; SQLite test DBs are always fresh so they skip it).
  - `/files/...` is now an authenticated route (owner-only, traversal-rejecting), replacing the old public StaticFiles mount; `?v=mtime` cache-busting behavior is preserved. `/api/state` iterates the owner's Project rows instead of scanning the projects dir, and shows a **placeholder card** (status Generating/Failed) for a project whose create-job hasn't written scenes.json yet — pre-queue such dirs were invisible, but now the row exists the moment Create is clicked and a failed create must not squat invisibly on its slug.
  - Dashboard (`web/index.html`): login/signup screen (shown on 401 or at boot via `GET /api/auth/me`), account email + Log out in the sidebar footer. Everything else (polling, action queue, auto-resume) untouched.
  - **Developer login button (added 2026-07, prefill design — an earlier same-day passwordless-endpoint version was deliberately replaced; don't reintroduce it)**: when `RENDERFLOW_DEV_LOGIN_EMAIL` + `RENDERFLOW_DEV_LOGIN_PASSWORD` are both set in the local `.env`, the login page shows a "⚡ Developer login" button that prefills those credentials and submits them through the **normal** `/login` (falling back to `/register` once on a fresh DB — so on a fresh DB the dev account becomes the admin and adopts legacy projects; register your personal email first if you want *it* to be admin). `GET /api/auth/dev-login` returns the prefill (or `{"enabled": false}` when unset — the deployed posture, exposing nothing); there is **no bypass endpoint**, the real password check always runs. Leave both vars unset on any deployed instance.
  - The API **refuses to start without `RENDERFLOW_SECRET_KEY`** (signs session cookies — generate with `python -c "import secrets; print(secrets.token_hex(32))"`).
  - **Deployment (Phase 3a, added 2026-07, `deploy/`)**: one Ubuntu 24.04 box — Docker for Postgres/Redis, API + worker in a host venv under systemd, Caddy for TLS; `deploy/README.md` is the runbook (`setup_server.sh <domain>` provisions everything idempotently; `deploy.sh` = pull + install + restart + health check; daily `backup.sh` via systemd timer, 14-day rotation, same-disk — off-site sync is a manual follow-up). `RENDERFLOW_ENV=production` flips session cookies to Secure and makes startup **refuse** if any dev flag (`RENDERFLOW_DEV_LOGIN_*`, `RENDERFLOW_DEV_CHECKOUT`) is set or the DB still uses the default `renderflow:renderflow` password (compose interpolates `RENDERFLOW_PG_PASSWORD` from `.env`). Linux portability handled in the same pass: `subtitles._FONT_CANDIDATES` now includes DejaVu/Liberation paths (macOS-only before — Linux captions would have silently used PIL's unreadable bitmap font), and Linux distro ffmpeg has drawtext, so the avatar disclosure banner (silently missing on the dev Mac) should burn in on the server — **verify both in the first server smoke test**. `uvicorn.run` gained `proxy_headers=True` (bind stays 127.0.0.1:8321; Caddy is the only public listener). Tests: `tests/test_production.py`.
- Local web dashboard (`renderflow/api.py` + `web/index.html`): FastAPI serves project state, live scene thumbnails, and queues `make_video.py` runs as Jobs for the Celery worker (create / resume / regenerate-scene). Finished renders are download-only by design (no inline player — client preference); the download card shows the project thumbnail. The download link's suggested filename is the project title (`downloadFilename(title, ext)` in `web/index.html`, sanitized for filesystem-illegal characters, `ext` defaults to `"mp4"`), not the on-disk `final.mp4` — client-side only, via the anchor's `download="..."` attribute; the file on disk is untouched. Verified live end-to-end. Dev stand-in for the Week-2 worker queue — pipeline never runs inside a request handler.
  **The project thumbnail (`thumbnail.jpg`) is downloadable too (added 2026-07)** — a second "Download thumbnail" link (`downloadFilename(p.title, 'jpg')`) sits next to "Download MP4" in the same card, no backend change needed since `thumbnail.jpg` was already served through the same `/files` static mount as `final.mp4`. The card itself now shows whenever *either* `p.videoUrl` or `p.thumbnailUrl` is set (previously gated on `p.videoUrl` alone) — the thumbnail is typically ready well before the final render, especially now that project creation pauses before rendering by default (see above), so its download link must not wait on the video.
  **"↻ New thumbnail" button (added 2026-07, same card)**: regenerates only the thumbnail via `POST /api/projects/{slug}/thumbnail/regenerate` → `make_video.py --thumbnail-only` (requires `--scenes-file`; runs `generate_thumbnail` + `render_thumbnail` and nothing else, ~5s with Pexels). Design constraints that shaped it, all verified live on a Complete project: (a) **the run must not demote a valid `final.mp4` to stale** — `generate_thumbnail`'s `save_plan` calls bump `scenes.json`'s mtime, tripping `final_ready`'s staleness check, so `make_video._regenerate_thumbnail` captures whether final was fresh *before* running and re-stamps it via `os.utime` in a `finally` (fresh stays fresh even on failure; genuinely-stale stays stale — never promoted); (b) the endpoint mutates nothing — the spawned run resets `plan.thumbnail` itself (a fresh `AssetRef`; COMPLETED is terminal, no legal transition out), keeping a single plan writer; (c) old `thumbnail.jpg` is deleted only *after* the new images generate (`render_thumbnail` skips when it exists — resume behavior), so a failed regenerate keeps the previous thumbnail downloadable; (d) dashboard-side it joins the unified action queue as `{type:'thumbnail', sceneId:null}` (queue label "⏳ Thumbnail queued", click again to cancel) but **never arms `pendingAutoResume`** — a thumbnail run doesn't invalidate the video, and auto-resume after it would fire an unwanted full render on a project the user paused mid-edit (`drainActionQueues` now sets the flag per-action-type, not unconditionally). Tests: `tests/test_thumbnail_regen.py` (freshness preserved / stale preserved / failure keeps old thumbnail).
- **Thumbnail images can use different providers than scene images (added 2026-07)**: `RENDERFLOW_THUMBNAIL_BG_PROVIDER` / `RENDERFLOW_THUMBNAIL_REACTION_PROVIDER` (config.py; empty = follow `RENDERFLOW_IMAGE_PROVIDER`) — `build_image(settings, name)` takes an optional name override, `generate_thumbnail(..., reaction_provider=)` accepts a second provider, and `make_video._thumbnail_image_providers` resolves both (reusing the main provider instance when names match, so rate-limit/dedup state stays shared). The user's current setup: scenes + reaction face from `pexels` (real photos), thumbnail background from `pollinations` (`RENDERFLOW_THUMBNAIL_BG_PROVIDER=pollinations` in `.env`) — client wants the clickbait background AI-generated (stock search rarely has the dramatic saturated composition) but the reaction face to be a real person photo. `plan.thumbnail.provider` records `"pollinations+pexels"` when they differ; cost still sums both. Verified live 2026-07 via the dashboard regenerate button.
- Project thumbnail: a **generated clickbait image + host reaction badge**, not a scene crop. `assets.generate_thumbnail()` extracts the topic from the title (`_topic_from_title` strips clickbait filler words — do NOT put the full title in the image prompt, the model renders it as garbled text; learned 2026-07), generates (a) a topic-literal dramatic background (subject right, no people) and (b) a separate **AI-generated reaction face** (`_thumbnail_reaction_prompt` — exaggerated shocked/amazed expression, built from the host's `AvatarSpec.description` with mood/expression phrases stripped out so they don't fight the reaction), both via the ImageProvider under one `plan.thumbnail` AssetRef (combined cost, one retry unit — thumbnails are cheap/non-critical). `render.render_thumbnail()` crops the background to 1280×720 `output/thumbnail.jpg` and composites the reaction face (`output/thumbnail_reaction.png`) as a white-ringed circular badge bottom-left; falls back to the plain `RENDERFLOW_AVATAR_IMAGE` portrait for older projects rendered before the reaction face existed, then to the first scene image if generation never ran. **Note: the reaction face is a fresh AI portrait matching the host's description, not a pixel-edit of the real avatar photo** — true identity-preserving editing (Pollinations' `kontext` image-to-image) needs the source photo hosted at a public URL, which a local file isn't; self-hosting one would be the path to a perfect identity match. The New Video modal has a "Make it clickbait" button that cycles the typed topic through title templates client-side, and a "🎲 Random topic (Claude)" button that now calls `POST /api/topics/random` (added 2026-09, see the dedicated note below) instead of picking from the old static bank.
- **Clickbait title text burned onto the thumbnail (added 2026-09)**: `render._overlay_clickbait_text(thumb, plan.title)` draws the bold all-caps project title across the top of `output/thumbnail.jpg`, called from `render_thumbnail()` right after `_overlay_host_badge()` (so the reaction badge is composited first, and the text — positioned along the top, badge sits bottom-left — never overlaps it). Pillow-composited like the intro/outro cards and captions, not asked of the image-generation model itself: 69labs/diffusion models render requested on-image text as garbled nonsense (same reason `_topic_from_title` keeps the literal title out of the background-image prompt, see above), so legible clickbait text has to be a separate deterministic drawing pass. Style: yellow fill with a thick black stroke (the classic YouTube-clickbait look, high contrast against any background), reusing `subtitles._font` for the bold-font lookup and `branding._wrap` for line-wrapping. **Adaptive sizing, not a fixed font size**: starts at 100pt and shrinks in steps to a 40pt floor until the wrapped text fits within the top ~42% of the frame's width/height — a short title (e.g. "Why Octopuses Have Three Hearts") renders large, a long one (e.g. "The Shark Older Than the United States") automatically backs off rather than overflowing the frame or overlapping the badge. Runs unconditionally as part of `render_thumbnail()` (not config-gated) — every project's thumbnail gets clickbait text, matching the client's request for "more clickbaiting look." No new AssetRef/state — it's a pixel-level post-process on the same `plan.thumbnail` asset, so `render_thumbnail()`'s existing resume-skip-if-exists behavior covers it too (regenerating requires the existing "↻ New thumbnail" button, which deletes and redraws the whole file). Verified live: applied directly to two already-rendered project thumbnails (no re-generation needed, $0 cost) and via `tests/test_pipeline_stub.py::test_overlay_clickbait_text_adds_visible_text` (pixel-level: some pixel in the top strip differs from the plain background) and `::test_overlay_clickbait_text_shrinks_long_titles_to_fit` (long title doesn't crash or resize the base image).
- Dashboard render-state rule (`api.py`, `final_ready` in `_project_view`): a `final.mp4` counts as done only if **no run is currently active for that project, all assets are completed, and the file is newer than scenes.json** (rewritten on every asset update). The `not run` clause matters on its own: ffmpeg creates the output file on disk the instant it starts encoding (with a fresh mtime, before any content is valid), so without it a still-rendering video could briefly look "ready" — the client explicitly caught this ("don't show the download button while it's still rendering") before the `not run` gate was added.
- **`_file_url()` (api.py) appends `?v=<mtime>` to every asset URL** (scene thumbs, project thumbnail, final video). Scene/thumbnail/video filenames are deterministic (`scene_002.png`, `thumbnail.jpg`, `final.mp4`) — resuming or regenerating overwrites the same path, so without the cache-buster the URL is byte-identical to before and the browser keeps showing the stale cached image/video. Reported by the client as "regenerate scene isn't changing anything" — the backend was correct all along, it was purely a browser-caching symptom.
- **"Regenerate scene" also varies the prompt now** (`api.py::_vary_prompt`, used by the `/regenerate` endpoint only — not the automatic per-scene generation or the face-check retry, which vary by seed alone). A fresh random seed on the *exact same* prompt text often keeps a similar composition since the prompt drives composition far more than the seed does; a manual regenerate appends a randomly-chosen framing instruction (" Try this take: from a different angle.", etc.), stripping any previous variation clause first so repeated clicks don't grow the prompt unbounded. Skipped for solo-layout scenes (no background image to vary). Verified live: prompt updated, new file mtime, new cache-busted URL, all consistent.
- **Regenerate no longer auto-renders the final video** — `make_video.py --skip-render` runs every asset step (images/voice/avatar/subtitles/thumbnail) and stops before `render_video()`. `regenerate_scene` (api.py) always spawns with this flag: re-rendering a 50+ scene video after every single-scene fix used to hold the "run active" lock for minutes, during which no other scene could be touched — client-reported as "I can't regenerate another scene." After a skip-render run, the project correctly shows **Paused** (all assets complete, but `final.mp4` was deleted and not yet rebuilt) with a "Resume run" button to do the one render pass once the user is done fixing scenes. Verified live: a single-scene regenerate now takes ~19s (was minutes), and the subsequent render-only resume takes ~22s since every asset is skip-eligible.
- **Initial project creation no longer auto-renders either (changed 2026-07)** — `create_project` (api.py) now spawns the very first `make_video.py` run with `--skip-render` too, same as regenerate. Previously the first run went straight from asset generation into `render_video()` in one subprocess, so the final MP4 was already rendered — with whatever avatar layouts and scene visuals the first generation pass happened to produce — before the user ever got to look at the scene grid. Client-reported: "it always renders even [though] the scenes or layout are not final yet." Now a brand-new project lands on **Paused** once assets finish, same as after a regenerate batch, so the user can review scenes, regenerate ones they don't like, or flip individual scenes to solo/split (now that `"auto"` always means split — see the avatar-layout note above) before clicking **Resume run** to do the one render pass. Note this project does **not** auto-fire that render the way a regenerate batch's `pendingAutoResume` does — `pendingAutoResume` (web/index.html) is only ever set by `drainActionQueues()` for a regenerate/layout action, never by `createProject()`, so the pause here is a deliberate stop, not a race to be closed.
- **"Generate from topic" in the New Video modal (added 2026-09, needs a funded `ANTHROPIC_API_KEY`)**: previously the dashboard's only create path was "paste a finished script" — `NewProject`/`create_project` (api.py) always built a `--script-file` argv, and `make_video.py --topic` (which calls `pipeline/script.py::generate_script` to have Claude write the *entire* narration + scene plan from a bare topic) was CLI-only, never reachable from the product. `NewProject` now accepts either `script` **or** `topic` (exactly one, 422 if both or neither) plus an optional `lengthMinutes` (clamped 1–15, topic mode only); topic mode enqueues `["--topic", topic, "--length", str(length_minutes), ...]` instead of writing a `source.txt` and passing `--script-file` — no make_video.py changes needed, it already supported `--topic` end to end. The topic text is still saved to `script/topic.txt` for provenance (mirroring `source.txt`) even though the pipeline never reads it back. `title` stays required and always wins over whatever title Claude would have picked (`make_video.py`'s existing `if args.title: plan.title = args.title`), so slug generation in the request handler needs no LLM call — the (potentially slow, billed) Claude call still only ever happens inside the worker subprocess, never in the request path.
  Dashboard: the New Video modal gained a "Paste script" / "✦ Generate from topic" segmented toggle (`state.newGenMode`); topic mode swaps the script textarea for a short topic textarea + a length dropdown (2/5/8/3 min) and submits `{title, topic, lengthMinutes, style}` instead of `{title, script, style}`. The 🎲 Random topic button forces the mode back to `'script'` first, since the idea it fetches now comes back as a ready-to-use short script (see below), not a raw topic for Claude to expand.
- **"🎲 Random topic" now asks Claude for a fresh idea instead of picking from a static bank (added 2026-09)**: the button used to pick from `RANDOM_TOPICS`, a fixed 10-entry array of pre-written title+script pairs hardcoded in `web/index.html` — it ran out (and started repeating) well before a real user's project count did, and every user got the exact same 10 ideas. `POST /api/topics/random` (api.py) now calls `pipeline/script.py::generate_topic_idea` (a short Claude completion via `GeneratedTopicIdea`, a small structured-output schema alongside `GeneratedScript` in schema.py) and returns one fresh `{title, script}` pair; the prompt is given the signed-in user's existing project titles and told not to repeat them (server-side, replacing the old client-side `state.projects` title filter). `RANDOM_TOPICS` and its "bank exhausted" alert are gone entirely.
  **Deliberately a plain synchronous call from the request handler, not a queued Job** — unlike full `--topic` script generation, which stays inside the worker subprocess specifically to keep billed Claude calls out of the request path (see the note above): this one completion is short (~100-200 output tokens, a couple seconds), so the same worker-subprocess indirection would only add latency for no real benefit. A failure (missing/invalid `ANTHROPIC_API_KEY`, rate limit, schema mismatch) returns 503 rather than a raw exception; the frontend (`web/index.html`'s `randomTopic()`, now async) alerts on any non-OK response, same pattern as `checkoutPlan`. `state.randomTopicLoading` (separate from the shared `state.busy`) drives a "🎲 Generating…" label on just that button while the request is in flight, without graying out the rest of the modal. Cost isn't tracked anywhere (there's no project yet to attach an `AssetRef` to) — logged via `LLMResult.cost` only, same as other untracked pre-project LLM calls.

- **Client-side unified action queue** (`web/index.html`: `state.actionQueues`, `drainActionQueues()`): only one `make_video.py` run may be active per project, so clicking "Regenerate" or changing a scene's avatar layout while a run is already active queues it instead of being blocked (regenerate button reads "Queue regenerate (run in progress)"; layout buttons show a ⏳ on the queued choice and stay clickable). - **Auto-resume after the regenerate batch finishes** (`web/index.html`: `state.pendingAutoResume`, `maybeAutoResume()`): every `regenerateScene` call (immediate or queued) marks that project's slug pending; `maybeAutoResume()` runs at the end of every `drainRegenerateQueues()` tick and fires `/resume` automatically the moment the project is idle (`!running`) with an empty queue and status `Paused`/`Failed` — no manual "Resume run" click needed after fixing one or several scenes. The pending flag is cleared *before* firing (not after), so a status swing through Rendering → Complete on the next polls can never re-trigger it. Verified via state-machine simulation (single regenerate, and a multi-scene queued batch) before trusting it live: exactly one resume fires per batch, never mid-queue, never repeated after Complete.

- **Currency normalization for speech** (`pipeline/text_normalize.py::normalize_for_speech`): Kokoro/Piper's espeak-based phonemizers read `$20,000` back digit-by-digit ("dollar two zero zero zero zero") instead of "twenty thousand dollars" — neither engine expands currency itself. A small dependency-free number-to-words converter expands `$`-prefixed comma-grouped amounts (with optional cents, e.g. `$20,000.50` → "twenty thousand dollars and fifty cents") and is applied in `assets.generate_voice()` **only to the string passed to `provider.synthesize()`**, never to `scene.narration` itself — captions (`pipeline/subtitles.py`) read the stored narration directly and should keep showing the numeral form on screen. Scoped narrowly to `$` currency patterns only (not general numbers/years) to avoid mangling things like dates. Not yet applied to ElevenLabs (cloud TTS generally normalizes currency itself) — revisit if that's shown to also mispronounce it.

- **YouTube publishing (added 2026-09, `renderflow/youtube.py` + `publish_youtube.py` + `scripts/setup_youtube.py`)**: a "▶ Publish to YouTube" button in the project detail view (shown once `videoUrl` exists) opens a modal (title/description/tags/privacy/synthetic-media checkbox, prefilled from the project title) and `POST /api/projects/{slug}/youtube/publish` enqueues a `Job(kind="youtube_publish")`. **Deliberate design choices from the client conversation, don't relitigate without asking again**: (a) one-click *per video*, not fully automatic after render — a human reviews before it goes out; (b) default privacy is **public** (the client's explicit choice after being shown the "start private" alternative — this is not the safe default you'd expect, it's intentional); (c) auth is one shared machine-level OAuth connection (`scripts/setup_youtube.py`, installed-app flow), not a per-user "Connect YouTube" flow — matches every other paid-provider credential in this app (one key per host). A real per-user flow would need a web OAuth redirect/callback in `api.py`, per-user token storage (DB columns on `User`, encrypted at rest), and a token-refresh job — worth doing before this ever leaves single-operator use.
  **Architecture**: `publish_youtube.py` is spawned as a subprocess exactly like `make_video.py` (multi-hundred-MB uploads take minutes — never inside a request handler); `tasks.py::SCRIPT_BY_JOB_KIND` maps `job.kind` to which script to spawn (`pid_is_pipeline`'s process-recognition check for cancellation was widened the same way). The result (`video_id`, `url`, `privacy_status`, `contains_synthetic_media`, `published_at`) is persisted at `<project>/youtube.json` (`schema.YouTubePublish`, `storage.save_youtube_publish`/`load_youtube_publish`) — **a file, not a DB column**, same pattern as `performance.json`: it's written by a spawned subprocess, and pipeline-adjacent scripts never touch the DB directly. `_project_view` surfaces it as `youtube: {...} | null` plus `youtubeConnected: bool`; once published the dashboard shows a "✓ View on YouTube" link instead of the button — **re-publishing isn't supported and would create a second, duplicate video** (the API has no "update this upload" concept here), so the button is deliberately replaced, not just disabled.
  **`status.containsSyntheticMedia`** (YouTube's altered/synthetic-content disclosure flag, added to the API 2024-10-30 — verified against live API docs before writing any code, not assumed) defaults `true` in both the modal and `upload_video()`, since every RenderFlow video is AI-narrated over AI-generated visuals. `SCOPES = ["youtube.upload"]` only — verified live-docs that this single scope covers both `videos.insert` and `thumbnails.set`, so there was no need for the broader (full read/write) `youtube` scope.
  **Live OAuth setup completed 2026-09; one real bug caught in the process**: `channel_title()` (the "confirm which account got connected" nicety in `setup_youtube.py`) 403'd with "insufficient authentication scopes" right after a *successful* token save — `channels.list` needs `youtube.readonly` or the full `youtube` scope, which the deliberately-minimal `youtube.upload` scope doesn't cover. Fixed by wrapping that one best-effort call in try/except (`setup_youtube.py`) rather than widening `SCOPES`, since doing so would grant the app more access than the actual upload feature needs just to support a cosmetic confirmation message. The Google Cloud Console UI has also been reorganized since this guide was first written: "OAuth consent screen" is now three tabs under **APIs & Services → Google Auth Platform** (Branding / Audience / Clients — direct links: `console.cloud.google.com/auth/branding`, `/auth/audience`, `/auth/clients`), and forgetting to add your own account under Audience → Test users produces `Error 403: access_denied` ("has not completed the Google verification process") on first sign-in — add yourself there and retry in the same browser tab.
  **Switching which Google account is connected** (e.g. moving from a throwaway test account to your real one) is just re-running `scripts/setup_youtube.py` — it unconditionally overwrites `.youtube_token.json`, no code change needed. Two gotchas hit live doing exactly this: (1) the new account also needs adding under Audience → Test users, same as the first account did; (2) running it while *already signed into a different Google account* in the same browser produced `Error 400: Bad Request` at a `signin/oauth/delegation?authuser=1...` URL — a multi-account session conflict, not a bug in this app. Fixed by opening the printed auth URL in a fresh **Incognito/Private window** instead of letting `run_local_server()`'s auto-opened tab reuse the existing multi-account session. This is also why `setup_youtube.py` reconfigures stdout for `line_buffering=True` on Windows (added the same 2026-09 troubleshooting session) — without it, the printed auth URL doesn't appear until the whole process exits (block-buffered, since a backgrounded process's stdout isn't a real console), which is useless when you need to hand that URL to a human *while the process is still paused waiting on the browser*.
  **A `final_ready` gotcha this feature exposed**: that computation used to be gated on a blanket `not run` (any active job hides the download link, since a *pipeline* run might be mid-write on `final.mp4`). A `youtube_publish` run never touches `final.mp4` — it only reads it — so blanket-hiding the download link while uploading would have been a UX regression (the video "disappearing" mid-publish). Fixed by renaming the gate to `rendering = run is not None and run.kind != "youtube_publish"` and using that instead of bare `run` in the `final_ready` check; a new `status == "Publishing"` (`STATUS_META`, purple) is shown separately so the two states read differently in the UI.
  **One-time setup this session did NOT and cannot do — it needs your own Google account**: (1) create/select a project at console.cloud.google.com; (2) APIs & Services → Library → enable "YouTube Data API v3"; (3) APIs & Services → OAuth consent screen → External, add an app name + your email, and add your own Google account under "Test users" (staying in **Testing** status avoids Google's app-verification review, fine for single-operator use); (4) APIs & Services → Credentials → Create Credentials → OAuth client ID → **Desktop app** → download the JSON and save it as `.youtube_client_secret.json` in the repo root (gitignored, like `.youtube_token.json`); (5) `pip install '.[youtube]'` then `python scripts/setup_youtube.py` once — opens your browser to Google's consent screen, approve as the test-user account whose channel should receive uploads, and the script prints the connected channel's name to confirm. The refresh token this produces is reused silently forever after (no repeated consent) until revoked.

Not built yet (roadmap order): subtitles (faster-whisper → ASS), narrator character consistency, more lip-sync avatar providers, real payment provider (Paddle/LemonSqueezy into the checkout seam), password reset (needs an email service), Next.js dashboard, per-user YouTube OAuth (see the publishing note above), YouTube Analytics API integration to pull views/watch-time automatically instead of typing them into the Revenue tab.

## Architecture — how a video gets made

```
make_video.py (CLI)
  [1] script:  topic --LLM--> GeneratedScript.to_plan() -> ScenePlan   (pipeline/script.py)
               or --scenes-file loads scenes.json directly (no LLM)
  [2] images:  per scene, ImageProvider.generate(image_prompt)          (pipeline/assets.py)
               talking_avatar scenes also get an avatar portrait
               (RENDERFLOW_AVATAR_IMAGE local file, or generated)
  [3] voice:   per scene, TTSProvider.synthesize(narration)             (pipeline/assets.py)
  [4] avatar:  talking_avatar scenes: AvatarProvider.generate_clip(
               portrait, voice, narration) -> lip-synced MP4            (pipeline/assets.py)
  [5] render:  per-scene clip (zoompan still, or avatar full/split),
               concat + loudnorm + faststart -> output/final.mp4        (pipeline/render.py)
```

Key mechanics that span multiple files:

- **`renderflow/schema.py` is THE central contract.** `ScenePlan` → `Scene` → `SceneAssets` (`image`, `avatar_image`, `voice`, `avatar_clip` as `AssetRef`s). Everything reads/writes these models; the plan is persisted to `projects/<slug>/script/scenes.json` after every asset state change. Treat schema changes like breaking API changes; update docs example and tests together. There is a parallel `Generated*` schema (what the LLM emits, no numeric constraints — unsupported by structured outputs) clamped into the real contract by `GeneratedScript.to_plan()`.
- **Asset state machine is exactly** `pending → running → completed | failed → retrying → running | cancelled`, enforced by `AssetRef.advance` (raises `InvalidTransition`).
- **Resume:** an asset with `status=completed` and a `path` is skipped on re-run. Consequence: config changes (voice, pacing, provider) do **not** retrofit an existing project — use a fresh `--slug` or delete the relevant `projects/<slug>/{voice,avatar}/` files.
- **Provider layer:** `providers/base.py` defines `Protocol`s (`LLMProvider`, `ImageProvider`, `TTSProvider`, `AvatarProvider`) returning `GeneratedAsset`/`LLMResult`; `providers/__init__.py` is the registry mapping env-selected names to adapters. `retry.py` supplies the backoff decorator adapters wrap their live calls with.
- **Rendering rules** (`pipeline/render.py`): scene duration always comes from ffprobe of the generated voice audio (or avatar clip) — never `duration_estimate_sec`. Scene visuals get **depth-parallax motion** by default (`pipeline/parallax.py`: Depth-Anything-V2-Small depth map + OpenCV remap, ~50 MB one-time HF download, ~2-5 s/scene on CPU; verified live 2026-07); `RENDERFLOW_MOTION=zoompan` opts out, and missing deps / depth failures fall back to zoompan automatically (flat Ken Burns, prescaled 2560×1440 to avoid sub-pixel jitter). Every talking-avatar scene renders split-screen by default (768px lip-synced avatar left, zoompan/parallax visual right) — full-screen solo is a per-scene opt-in, not automatic (see the avatar-layout note above); the local splitter marks **every** scene `talking_avatar` by default, so the host is on camera for the whole video either way — unless `RENDERFLOW_LOCAL_AVATAR=0` (see below), which keeps those scenes plain narration instead. Audio is loudness-normalized per clip; final concat re-encodes with `+faststart`.
- **File formats ripple:** Piper emits WAV, ElevenLabs MP3 — `pipeline/assets.py` derives the file extension from `asset.meta["format"]`; lip-sync models want WAV, so `providers/avatar/postprocess.py` transcodes. That module also burns the "AI-generated host" disclosure banner into every avatar clip — **but the burn-in silently degrades to no banner when ffmpeg lacks `drawtext`, and the dev machine's ffmpeg build has no drawtext filter (discovered 2026-07), so local clips currently ship without the disclosure.** Fix path: reinstall ffmpeg with libfreetype, or overlay a pre-rendered PNG instead of drawtext.
- **YouTube Shorts — vertical 9:16 output (added 2026-09, v1 scope)**: a project-level format choice, `ScenePlan.format: "landscape" | "shorts"` (`schema.VideoFormat`, defaults `"landscape"` — old scenes.json files load fine, no migration). Set at creation via `--format` (`make_video.py`) or the dashboard's New Video/New Short buttons; not changeable afterward (same as the title — there's no "convert an existing project to Shorts" path).
  **What "shorts" actually changes**: `render.py::_dims_for(plan)` returns `(SHORTS_WIDTH, SHORTS_HEIGHT) = (1080, 1920)` instead of `(WIDTH, HEIGHT) = (1920, 1080)`, threaded through as explicit `width`/`height` params on every clip-rendering function (`render_scene_clip`, `_render_broll_clip`, `render_avatar_full_clip`, `_zoompan_expr`) — default arguments equal to the landscape constants, so every existing call site is unaffected. `render_video()` is the only caller that resolves `_dims_for` and passes it down. Split-screen avatar has no room in a 9:16 frame, so `render_scene_clip` falls back to full-screen solo (`render_avatar_full_clip`) for **any** talking-avatar scene whenever `height > width` — a portrait-orientation check, not a shorts-specific flag, so a future non-landscape format gets this for free. `create_project` (api.py) always forces `lengthMinutes` to `1.0` for shorts server-side (never trusts the client body — the New Video modal already hides the length picker for shorts, showing "~1 minute, no length to choose" instead, but the backend re-clamps anyway).
  **v1 deliberately skips, rather than teaches to render vertically**: intro/outro cards (`_branding_clips` returns `([], [])` when `plan.format == "shorts"` — `_render_card_clip` still only knows `WIDTH`/`HEIGHT`) and the AI clickbait thumbnail (`generate_thumbnail`/`render_thumbnail` skipped; `render.render_shorts_thumbnail()` grabs a single frame from the finished `final.mp4` instead — $0 cost, but only exists once the video is actually rendered, so a shorts project shows no thumbnail while Paused, unlike a landscape project's AI thumbnail generated during the asset phase). Revisit each of these independently if Shorts quality needs to catch up to landscape rather than staying a fast, low-cost first pass.
  **Captions DO run for shorts (added 2026-09, same day as the format itself)**: initially skipped alongside cards/thumbnail, but that was the wrong call — burned-in captions matter *more* for phone-viewed vertical video, not less. `pipeline/subtitles.py::render_caption_png`/`write_scene_subtitles` gained a `width` param (default `CANVAS_W=1920`, unchanged for landscape) — the caption PNG's own width must equal the actual output frame width, or `render.py`'s centering overlay (`(W-w)/2` at ffmpeg runtime) either clips it (PNG wider than the frame) or leaves it undersized with wasted margin (narrower). `pipeline/assets.py::generate_subtitles` resolves the right width via the new `render.dims_for(plan)` (promoted from a private `_dims_for` to a proper cross-module helper — the first production, non-test caller of a render.py dims helper from outside render.py). Shorts now follows the same `RENDERFLOW_SUBTITLES` toggle as landscape — no shorts-specific override; a shorts project's captions can still be turned off the normal way. Verified live: forced `RENDERFLOW_SUBTITLES=1` temporarily (this dev machine's `.env` normally has it `0` — B-roll-heavy landscape videos already look like produced footage, see the note below), rendered a real shorts video, and extracted a frame confirming the caption text sits correctly centered and unclipped at 1080px width, not stretched or cut off from a stale 1920px assumption. `.env` restored to its original value after the check.
  **Real bug found and fixed building this, unrelated to the vertical resolution itself**: concatenating a zoompan-rendered clip with a scale+crop-rendered clip (e.g. one solo-avatar scene next to one plain-narration scene) failed with ffmpeg's `concat` filter error "Input link parameters do not match the corresponding output link parameters" — two different filter chains, scaling the *same* landscape test source into the *same* portrait target, each rounded to a different near-1-but-not-exactly-1 SAR (sample aspect ratio, e.g. `40960:40959` vs `10240:10239`) to compensate for a non-integer scale factor, and `concat` requires every input's SAR to match exactly. Landscape (16:9) never hit this because `PRESCALE_W/H` is an exact integer multiple of `WIDTH/HEIGHT`, so the scale factor was always a clean whole number with nothing to compensate for. Fixed by appending `setsar=1` as the last step of every clip-ending filter chain (`_zoompan_expr`, `render_avatar_full_clip`, `render_avatar_split_clip`, `_render_broll_clip`, the parallax-visual branch of `render_scene_clip`, `_render_card_clip`) — forces a clean 1:1 SAR regardless of which filter path produced the clip or what aspect ratio is in play, so the whole class of near-1 SAR mismatches can't recur. Caught by a real-ffmpeg integration test mixing an avatar-solo scene with a plain-narration scene at shorts dimensions (`tests/test_pipeline_stub.py::test_render_shorts_produces_vertical_video_and_thumbnail`) — would not have been caught by a same-path-only test.
  Dashboard: a new **Shorts** nav tab (icon `▯`, between Projects and Activity) shows only `format === "shorts"` projects — mirrors the Projects screen exactly (`projectsGridHtml()`, extracted from the old `projectsScreenHtml()` so both tabs share one card-grid renderer instead of duplicating ~40 lines of card markup; `cardAspect: 'shorts'` renders a taller thumbnail box, 220px vs landscape's 130px, so a vertical thumbnail doesn't look squashed). "+ New Video" (Projects) and "+ New Short" (Shorts) both open the same modal via `openModal(format)` — the format arg (not a modal-internal toggle) decides which format gets created, shown back to the user as a "New Short" title + "▯ 1080×1920" badge when it's the shorts button. `_placeholder_view` (api.py) reads `format` back from the create job's own `argv` (`--format` isn't written to `scenes.json` until the job actually runs), so a just-clicked Short shows up under the Shorts tab immediately, not just once assets finish generating.

## Hard rules

- **Never call an external API from business logic.** Everything goes through the `Protocol` interfaces in `providers/base.py` and the registry in `providers/__init__.py`. Fix response-shape problems in the provider adapter, not the pipeline.
- **Cost tracking from day one.** Every provider call records its cost on the asset/result; the system must always be able to answer "this video cost $X".
- **Never commit `.env`.** Keys live only there. `.env.example` documents the variables.
- Backend stays Python-only. Type hints everywhere; Pydantic for schema and API contracts.
- Keep changes minimal and surgical — Week 2 (workers, Postgres, FastAPI) will build on this structure; don't restructure preemptively.

**"Maximize 69labs" combo, live-verified 2026-09**: `RENDERFLOW_IMAGE_PROVIDER=labs69` + `RENDERFLOW_TTS_PROVIDER=labs69` + `RENDERFLOW_BROLL_PROVIDER=labs69` runs images (fallback stills + thumbnail), voiceover, and B-roll all through 69labs. Two things to know before flipping this on: (a) **images are generated for every scene even though B-roll almost always supersedes them** — `generate_images` runs unconditionally as the fallback-if-broll-fails safety net (see the B-roll notes above), so this combo pays for a labs69 image *and* a labs69 video per scene, not one or the other; (b) pair it with `RENDERFLOW_SUBTITLES=0` (previous note) — real generated video footage doesn't need burned-in captions on top.
**`RENDERFLOW_THUMBNAIL_BG_PROVIDER`/`_REACTION_PROVIDER` pinned to `labs69` explicitly (added 2026-09)**, not just inherited from `RENDERFLOW_IMAGE_PROVIDER` — keeps the clickbait thumbnail on 69labs even if the main scene image provider ever changes (e.g. back to `pollinations` for cost, while keeping the thumbnail — the one image every viewer actually sees before clicking — on the better model). No prompt changes needed: `_thumbnail_prompt`/`_thumbnail_reaction_prompt` (`pipeline/assets.py`) were already explicitly clickbait-styled ("Viral YouTube thumbnail background... extreme contrast, vivid saturated colors" / "Exaggerated shocked and amazed expression... dramatic YouTube thumbnail reaction shot") from when this feature was first built — 69labs just executes those prompts noticeably better than the free stack. Verified live: regenerated the octopus video's thumbnail and got a genuinely publish-quality result — glowing hearts rendered directly into the octopus illustrating the video's topic, convincing shocked reaction face.

**Claude rewrites each scene's prompt for AI video generation (added 2026-09, `pipeline/script.py::rewrite_video_prompt`)**: `labs69_video.py` originally fed the video model the exact same prompt built for a *still image* — a static-photo caption ("35mm documentary photograph, shallow depth of field...") — which wastes a video model's actual ability to show movement. `make_video.py` now builds an LLM (only when `broll.name == "labs69"` — never for `pexels-video`, whose keyword-search adapter would break on a motion-descriptive prompt) and `generate_broll` (`pipeline/assets.py`) calls `rewrite_video_prompt` per scene before `find_clip`, turning e.g. "Macro underwater shot of feathery octopus gill structures..." into "...gill filaments as they pulse and undulate gently... camera drifts slowly closer... particles float past in the current..." (verified live). Cost is folded into `scene.assets.broll.cost` alongside the video generation cost (a few tenths of a cent per scene via Claude — leverage on the much larger 69labs video spend, not a meaningful cost on its own). **Pure best-effort, exactly like the B-roll step it feeds**: any rewrite failure (missing `ANTHROPIC_API_KEY`, rate limit, whatever) is caught in `generate_broll` and falls back to the original still-photo prompt for that scene — never blocks or fails B-roll, which stays optional end to end either way.

SaaS layer: `RENDERFLOW_DATABASE_URL` (defaults to the docker-compose Postgres), `RENDERFLOW_REDIS_URL` (Celery broker/backend), `RENDERFLOW_SECRET_KEY` (session-cookie signing — **required**, the API refuses to start without it; the CLI pipeline ignores all three). Local-dev-only flags (leave unset when deployed): `RENDERFLOW_DEV_LOGIN_EMAIL`/`_PASSWORD` (login-page prefill button), `RENDERFLOW_DEV_CHECKOUT` (instant no-payment plan activation — the future payment-provider seam).

## Provider notes (learned the hard way — do not rediscover)

- **A local security product's HTTPS scanning can break every httpx-based provider with `CERTIFICATE_VERIFY_FAILED: unable to get local issuer certificate` — fixed globally via `truststore`, added 2026-09.** Root cause, verified live: Avast's "Web Shield" HTTPS scanning MITMs outbound TLS and re-signs it with its own root CA (`Avast Web/Mail Shield Root`), which Avast installs into the *Windows* trust store — so curl and browsers (which consult the OS store) connect fine, but every `httpx` call (every provider, and the `anthropic` SDK) failed, because `httpx`/`certifi` verify against a bundled Mozilla CA list that has no way to know about a locally-injected root. Reproduced against `69labs.vip` (`openssl s_client` showed the Avast-issued leaf cert); any HTTPS provider a security product decides to intercept is equally exposed, on any user's machine, not just this one. Fixed in `renderflow/__init__.py`: `truststore.inject_into_ssl()` (core dependency, pyproject.toml) monkeypatches `ssl.SSLContext` so verification goes through the OS's native trust store instead of `certifi` — matching curl/browser behavior with no antivirus setting to change and no cert bundle to hand-patch. Runs at package import time, before any provider constructs an httpx client. Verified live: a project that had failed every scene's image/voice generation with this exact error succeeded on every scene on retry after the fix, no other change.
- **`ffmpeg-still`'s disclosure-banner `drawtext` filter segfaults ffmpeg outright on this Windows box, instead of failing gracefully — fixed with an explicit `fontfile=`, added 2026-09.** Root cause, verified live by reproducing the exact filtergraph at the command line: fontconfig can't find its default config file (`Fontconfig error: Cannot load default config file: File not found`), and rather than erroring cleanly, this ffmpeg build (`9.0.1-full_build`, gyan.dev) crashes with SIGSEGV — no error text beyond the version banner, so `providers/avatar/ffmpeg_still.py`'s existing `"No such filter: 'drawtext'"` fallback (written for a *different*, older bug — the dev Mac's ffmpeg build lacking drawtext entirely, see the Rendering-rules note below) never triggers; the process is just gone, and every scene's avatar clip fails. Fixed by adding `providers/avatar/ffmpeg_still.py::_drawtext_font_arg()`, which passes an explicit `fontfile=` pointing at a real font file, bypassing fontconfig entirely — reuses `subtitles._FONT_CANDIDATES`/a new `subtitles._resolve_font_path()` (the same cross-platform font search already used for Pillow-rendered captions/cards) instead of a second font search. Falls back to ffmpeg's original fontconfig-based lookup (unchanged behavior) when no candidate font exists on the host. Verified live: the exact failing filtergraph, reproduced with `fontfile=` added, exits 0 and produces a valid clip; a project that had failed every scene's avatar clip with this segfault succeeded on every scene on retry after the fix.
- **Worker auto-retries a failed pipeline run up to `MAX_RUN_ATTEMPTS = 10` times before giving up (`tasks.py::run_pipeline`, added 2026-09)**: motivated directly by the truststore fix above — a run had failed 100% of its scenes on a transient local error, and the only way to recover was noticing the "Failed" status and clicking Resume by hand. Safe specifically because `make_video.py` is resumable: a completed asset skips on re-run (`AssetRef`'s state machine), so re-invoking the exact same argv after a failure just picks up whatever didn't finish, never redoes completed work or duplicates output. Applies only when `SCRIPT_BY_JOB_KIND` resolves to `make_video.py` — **`youtube_publish` keeps the original single-attempt behavior**, since it's a one-shot, human-reviewed action with no such resumability (retrying a real auth/quota failure blindly would just hammer the API pointlessly, not recover anything). Each attempt gets its own `=== ... attempt N/10 ===` header in `run.log` (all attempts append to the same file, so the existing `_log_tail` error reporting — which reads the file's last N chars — naturally surfaces the most recent attempt); a `RUN_RETRY_DELAY_SEC = 5` pause separates attempts, and cancellation is checked both before starting the next attempt and right after each one finishes, so a mid-retry cancel can't be raced by a fresh spawn. `job.started_at` is stamped once, on the first attempt, so `productionTimeSec` still spans the whole retry sequence rather than resetting per attempt. Tests: `tests/test_jobs.py` (`test_run_pipeline_retries_and_recovers`, `test_run_pipeline_does_not_retry_youtube_publish`; the existing failure test now asserts all 10 attempts ran).
- **ElevenLabs free tier blocks "library" voices over the API** (402 `paid_plan_required`). Only the account's *premade* voices work — e.g. George `JBFqnCBsd6RMkjVDRZzb` (documentary storyteller). Free tier = 10k chars/month, **no commercial rights**.
- **Pollinations** is keyless/free but anonymously caps at 1024×576 regardless of requested size (re-verified 2026-07); the renderer upscales, so output is 1080p but soft. A free registered token from auth.pollinations.ai (set `POLLINATIONS_TOKEN`) is sent as a Bearer header and lifts limits/watermark — whether it unlocks true 1080p is untested (no token yet). No `negative_prompt` input — the adapter folds it into the prompt. Can be slow (30–60 s/image). **Rate limits are real and sticky**: anonymous = 1 request/15 s, registered = 1/5 s; bursting past them earns persistent 429s that outlive short retries (hit 2026-07 after a 59-scene run). The adapter self-throttles to the allowed interval and retries with 20–60 s backoff — budget ~15-20 s/image anonymous.
- **Kokoro** (`kokoro-onnx`, Apache-2.0 — commercial OK) is the default narrator: far more natural prosody than Piper, runs local CPU faster than realtime, 24 kHz WAV. Setup: `pip install '.[kokoro]' && python scripts/setup_kokoro.py` (~340 MB into `.kokoro/`). Current voice `am_michael` (warm US male); alternates `bm_george` (older British), `am_onyx` (deep US), `am_fenrir`, `bm_fable`. `speed` = 1/`RENDERFLOW_TTS_LENGTH_SCALE` (mapped in make_video); sentence pauses inserted like Piper. No literal breath sounds — that tier is paid (ElevenLabs).
- **Piper** voices live in `.voices/` (~60 MB each). MIT license — commercial use OK. Downloaded: `en_US-john-medium` (deep older male), `en_US-lessac-medium`, `en_US-ryan-low`. Fast but robotic — replaced by Kokoro as default 2026-07.
- **Pexels** (`providers/image/pexels.py`, `RENDERFLOW_IMAGE_PROVIDER=pexels`): free stock-photo **search** instead of AI generation — real photos, $0 cost. Free `PEXELS_API_KEY` from pexels.com/api (200 req/hr, 20k/month); license allows commercial/monetized use, no attribution required (photographer + photo URL recorded in asset meta anyway). **History: an earlier Pexels provider was removed 2026-07 for the client rule "visuals must be AI-generated, no stock photos/footage"; this one was rebuilt 2026-07 at the user's request — confirm the rule is actually lifted before shipping client videos with it.** Mechanics that differ from generation providers: (a) search wants 2-4 keywords, so `_search_query()` extracts topic/excerpt from the known prompt shapes (`_local_image_prompt`, `_thumbnail_prompt`) via regex — **if those prompt builders' wording changes, update the regexes** — with a stopword-filter fallback for any other prompt, and progressively shorter queries on zero results; (b) there is no seed, so the face-check retry gets a *different photo* via per-query used-id exclusion, and cross-process regenerates avoid repeating the same photo by picking randomly from the top 10 results; alt-text that looks face-y ("portrait", "selfie"…) is deprioritized before `facecheck` judges the actual pixels; (c) **set `RENDERFLOW_AVATAR_IMAGE`** — the avatar-portrait and thumbnail-reaction calls go through the same ImageProvider, and a stock search can't produce a consistent host matching an `AvatarSpec` description (it returns some random stock person). **Verified live 2026-07** (key in `.env`, now the active image provider): `check_providers.py image` passes, and a real scene prompt ("salesman promised the roof would pay for itself" / topic "solar panels") extracted query `solar panels salesman promised roof pay` and returned an on-topic, face-free 7952×5304 rooftop-panels photo — originals are far higher-res than Pollinations' 1024×576 cap.
- **dotenv gotcha:** `Settings.load()` uses `load_dotenv(override=True)` — `.env` is the source of truth even for pipeline subprocesses spawned by a long-running API server (without override, the server's stale inherited env pinned subprocess config; hit 2026-07 when a TTS switch didn't apply).
- **Piper pacing:** raw Piper sounds rushed. `RENDERFLOW_TTS_LENGTH_SCALE` slows delivery; the adapter also splits text on `.!?…` and inserts `RENDERFLOW_TTS_SENTENCE_PAUSE` seconds of silence between sentences (an ellipsis in narration earns a dramatic pause). Remember the resume gotcha: existing projects keep their old audio.
- **Wav2Lip avatar** (`wav2lip-local`): `scripts/setup_wav2lip.py` pulls code **and** weights from the `camenduru/Wav2Lip` HF mirror into `.wav2lip/` (~520 MB — the official OneDrive checkpoint links are dead) and patches `audio.py` for librosa ≥ 0.10 (kwargs-only `filters.mel`). Runs ~real-time on Apple-Silicon CPU (13 s narration → 15 s). Lips only — the model doesn't move the head, so the adapter adds a slow zoompan push-in; for real head motion use `sadtalker-replicate`. Verified live 2026-07.
  **Bug fixed 2026-07: lip sync drifting worse toward the end of longer videos.** `wav2lip_local.py`'s finishing pass encodes each raw clip at `FPS = 25` (Wav2Lip's native output rate), but `pipeline/render.py`'s timeline is `FPS = 30` everywhere else (zoompan, parallax visuals both explicitly filter `fps=30`). `render_avatar_full_clip`/`render_avatar_split_clip` scaled/cropped the avatar video channel but never added an `fps={FPS}` conversion, so avatar segments stayed at 25fps while spliced into an otherwise-30fps concat timeline. Each clip's own audio/video was internally fine (same source), but the per-clip timebase mismatch compounded across dozens of concatenated scenes, showing up as growing audio/lip drift by the end of a long video. Fix: added `fps={FPS}` to both functions' avatar-channel filter chain (right before `tpad`), normalizing every clip to the same CFR before concat.
- **SadTalker avatar** (`cjwbw/sadtalker` on Replicate, version pinned in the adapter): billed per GPU second, so cost scales with narration length (~$0.08–0.15 for a short clip; cost computed from `predict_time`). Defaults `preprocess=full`, `still_mode=False` (head motion), `use_enhancer=True`; if the background warps around the moving head, set `still_mode=True`. The account's Replicate token exists but is **unfunded** — a credit purchase (min $10) is required, a saved card is not enough (402 `Insufficient credit`).
- **MEMO avatar** (`memo-hf`, public `fffiloni/MEMO` Gradio Space via `gradio_client`): demo-grade only — the Space **trims input audio to 4 seconds** and requests a 240s ZeroGPU slot that anonymous users are refused outright; a free `HF_TOKEN` is required just to be admitted. Verified 2026-07: every public talking-head Space has similar guards (EchoMimic trims to 5s / requests 200–300s). **There is no free hosted lip-sync API fit for full-length scene narrations.** Also: `gradio_client>=2` renamed `hf_token=` to `token=`, and needs `httpx_kwargs={"timeout": httpx.Timeout(30, read=None)}` or long generations die with `ReadTimeout`.
- **69labs** (`providers/labs69_client.py` + `image/labs69.py`, `tts/labs69_tts.py`, `video/labs69_video.py`; added 2026-09 at user request): a single paid job-queue API (`69labs.vip/api/v1`, one `LABS69_API_KEY` for all three) covering images, TTS, and true AI video generation. All three adapters share `Labs69Client` for the submit→poll→download lifecycle instead of duplicating it — see that module's docstring for why it hand-rolls its own retry loop (with a *reused* `Idempotency-Key` per logical request) rather than wrapping calls in `retry.py`'s `@retryable`, which would mint a fresh key — and therefore a fresh billed job — on every retry.
  **Bug fixed 2026-09: `Labs69Client.download()` had no retry at all**, unlike `submit()`/`poll_until_terminal()` — hit live on a real ~4 MB video B-roll clip (`httpx.RemoteProtocolError: peer closed connection without sending complete message body`, mid-download). A multi-megabyte transfer has a meaningfully higher chance of a mid-stream drop than the small JSON responses the other methods handle, so it earned its own retry (3 attempts, exponential backoff, catches `httpx.TransportError`). The scene survived fine either way — `generate_broll`'s per-scene continue-on-failure caught it and fell back to the still image, exactly as designed — but the retry means a transient network blip no longer costs a whole paid clip.
  **Cost tracking is honest-but-incomplete for credit-based 69labs accounts**: `cost_from_status()` reads the USD `billing.totalAmountCents` block, which only pay-per-use accounts get; a credit-plan account's job status has `billing: null`, so `GeneratedAsset.cost` comes back `None` (excluded from `ScenePlan.total_asset_cost`, per existing `AssetRef.cost` semantics) rather than being reported as `$0` — the actual per-job cost on a credit plan is simply not visible to RenderFlow. If dashboard cost accuracy matters on a credit plan, prefer a pay-per-use 69labs key.
  **TTS**: `voice` (i.e. `RENDERFLOW_TTS_VOICE`) is passed straight through as `voiceId`; it must be an ID valid for whichever wire `voiceProvider` you've configured (`RENDERFLOW_LABS69_VOICE_PROVIDER`, default `elevenlabs`) — an ElevenLabs voice ID and a MiniMax catalog voice ID are not interchangeable. `CENSORED` status is treated as a hard failure (`Labs69Error`), not recovered automatically — 69labs' `/tts/retry-censored` chunk-rewrite flow isn't wired up; a censored line needs a manual narration edit and a resume/regenerate.
  **B-roll (video generation)**: `labs69_video.py` is generation, not search, so it feeds the scene's *full* `image_prompt` (plus `negative_prompt`, folded in like pollinations) straight to the model instead of reducing it to search keywords the way `pexels_video.py` must. Valid `duration`/`aspectRatio` values are read from `GET /videos/models` at call time (cached per provider instance) rather than hardcoded, since the docs explicitly warn these change over time. **This is a deliberate reversal of the "no AI video generation" cost-control rule below** — it's opt-in (`RENDERFLOW_BROLL_PROVIDER=labs69`), `pexels-video` remains the $0 default.
- **Claude LLM step:** uses structured outputs (`output_config.format` with `GeneratedScript.model_json_schema()`); the generation schema deliberately has no numeric constraints (unsupported there) — bounds are clamped in `GeneratedScript.to_plan()`.
  **Bug fixed 2026-09, first live run with a funded `ANTHROPIC_API_KEY`**: every `--topic`/`--llm-split` call 400'd with `output_config.format.schema: For 'object' type, 'additionalProperties' must be explicitly set to false`. Anthropic's structured-output feature requires that key on **every** object-typed schema node; Pydantic's `model_json_schema()` only emits it for models with `model_config = ConfigDict(extra="forbid")` — most of the `Generated*` models have that, but `AvatarSpec` (shared with the real, non-generation `Scene` schema, which has no reason to forbid extra fields) doesn't, so its nested schema silently violated the requirement. This had never been caught because the feature was never exercised against a live key before (see "no `ANTHROPIC_API_KEY` funded yet" note in earlier sessions). Fixed with `providers/llm/claude.py::_closed_schema()` — recursively walks the schema dict (including `$defs`) and sets `additionalProperties: false` on any object node missing it, applied right before the request — instead of chasing this down per-model, since a future nested model could just as easily forget the config. Verified live via a direct `generate_script()` call (not just `check_providers.py claude`, which only does a plain non-structured ping and would never have caught this).

## Testing conventions

- Stub providers in `tests/stubs.py` satisfy the Protocols — use them; never hit live APIs in tests.
- SaaS-layer tests (`tests/conftest.py`) run the SQLAlchemy models on in-memory SQLite (StaticPool) and stub `run_pipeline` at the api boundary — no Postgres, Redis, or Celery broker needed. `Settings.load` is monkeypatched wholesale (env vars don't work — `load_dotenv(override=True)` clobbers them with .env). Two `TestClient`s = two users (separate cookie jars) for isolation tests.
- The FFmpeg integration test generates media with lavfi and is skipped when ffmpeg is absent.
- Live provider verification is `scripts/check_providers.py`, run manually, never in CI. The `avatar` check is excluded from the default run (slow; costs money on paid providers).

## What NOT to do

- Don't generate AI video clips by default (only stills + motion) — cost control, Phase 4+ decision. `pexels-video` (free stock footage) is still the default B-roll route. **Exception, added 2026-09**: `RENDERFLOW_BROLL_PROVIDER=labs69` is a deliberate, user-requested, opt-in reversal of this rule for accounts willing to pay per clip — see the 69labs provider note above. Don't extend AI video generation anywhere else (e.g. don't make it the default, don't add another AI-video B-roll provider) without the same explicit confirmation.
- Don't build auth, billing, publishing, or dashboards before the pipeline they'd serve exists.
- Don't render synchronously inside API requests once the FastAPI layer exists (Week 2+) — queue it.
- Don't change the scene schema casually, and don't bypass the provider registry.
